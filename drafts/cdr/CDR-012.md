# CDR-012: GitLab Text Writes Must Go Through UTF-8 File or STDIN

## Context

On Windows shells (PowerShell 5.1, codepage 866/1251) passing Unicode text
(typographic symbols like paragraph marks, arrows, box-drawing) inline via
`glab ... --message "<text>"` mangles it into mojibake on GitLab issue/MR
notes, descriptions, and milestones. The corruption happens at the CLI
argument boundary, not on the GitLab side — GitLab stores and renders UTF-8
correctly when it receives intact bytes.

## Decision

All agent-initiated GitLab text writes (issue notes, MR notes, issue/MR
descriptions, milestone text) MUST pass the body through a UTF-8 file or
STDIN pipe — never through an inline `--message`/`-m` CLI argument.

Concrete paths (first available wins):

- `glab issue note` / `glab mr note create|update`: pipe via STDIN or
  redirect from a UTF-8 file (`glab mr note create 123 < body.md`).
- `glab issue create|update` / `glab mr create`: use `--description-file`
  (file or `-` for STDIN).
- `glab api` JSON writes: use `--input <file>` (or `--input -`) instead of
  `-f`/`--raw-field` with inline Unicode values.
- Before piping on Windows: `[Console]::OutputEncoding =
  [Text.UTF8Encoding]::UTF8` (and `chcp 65001` where applicable).

## Rejected Alternatives

- Inline `--message` with Unicode on Windows shells — corrupts symbols at
  the argument-encoding boundary; each touch rewrites good text into garbage.
- Stripping Unicode symbols from texts — removes useful readable markers
  (paragraph, arrows) that users want to keep.
- Post-hoc fixing mojibake after posting — each rewrite compounds the damage.

## Reason

File/STDIN transport preserves exact UTF-8 bytes end-to-end, so readable
Unicode markers survive every agent touch of a task, MR, or milestone.
Inline CLI args are the single corruption point; bypassing it eliminates
the entire mojibake class without restricting the symbol set.
