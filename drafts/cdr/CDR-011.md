# CDR-011: Post-Review PR Merge and Tracker Closure Protocol

## Context

After a Pull Request is reviewed by `factory-review` and declared `outcome=merge-ready`, agents often resort to uncontrolled manual actions: merging directly into `main` via git, modifying project-level planning documents (`roadmap.md`), or leaving tracker lifecycle labels inconsistent (`factory-stage:validation` instead of `factory-stage:done`).

## Decision

The post-review closure protocol must strictly follow a 4-step sequence:
1. **Separation of Duties**: `factory-review` is strictly non-approving and non-merging. Merge execution requires explicit code-owner authorization.
2. **Standard Host Merge**: Merge the approved PR/MR via the tracker host CLI or API (e.g., `glab mr merge <id> --merge-commit --remove-source-branch`) at the exact reviewed head SHA.
3. **Tracker Lifecycle Synchronization**: Update the governing ticket lifecycle labels to `factory-stage:done` (unlabeling previous execution/validation stages).
4. **Planning Document Immutability**: Agents must never manually modify canonical plan files like `docs/adlc/product/roadmap.md` during PR closure; `roadmap.md` is updated solely through dedicated planning skills (`factory-queue plan`).

## Rejected Alternatives

* Ad-hoc `git merge` in root — bypasses branch protections, CI triggers, and tracker merge hooks.
* Updating `roadmap.md` per individual ticket — breaks SSOT and causes drift against tracker state.

## Reason

Enforcing this standard protocol eliminates inconsistencies in tracker states and protects repository integrity from unauthorized direct modifications.
